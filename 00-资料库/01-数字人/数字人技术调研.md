## 本节速览

1. **[事实]** 开源口播数字人已形成清晰的"三层分工"：**底层唇形替换**（MuseTalk / Wav2Lip / LatentSync，只改嘴部，保留原视频）→ **中层肖像驱动**（Hallo / Hallo2 / Sonic / FLOAT / EMO，单张图 → 整脸动态）→ **上层全身生成**（字节 OmniHuman-1，单图 + 音频 → 半身/全身）。层次越高，GPU 成本和"不像本人"风险越高。
2. **[事实]** 真正的"实时"目前只有一条路：MuseTalk 官方称在 NVIDIA Tesla V100 上可达 30fps+，且**不是扩散模型**，是单步隐空间 inpainting；但其人脸区域固定 256×256，官方自述存在"胡子、唇形唇色保留不佳"和"单帧生成导致的抖动"三项局限。
3. **[事实]** 许可证是这个赛道最大的坑：LivePortrait 代码是 MIT，但仓库 LICENSE 明确写明 **InsightFace 模型仅限非商业研究**，商用须替换检测模型；**DUIX/HeyGem 使用非标准 "DUIX.COM Community License"，MAU > 1000 必须另行申请商业授权，并强制在产品上标注 "Built with DUIX.COM"**。
4. **[事实]** 合规上有一条硬约束常被漏掉：《深度合成管理规定》第十四条要求，提供人脸/人声编辑功能时**必须提示使用者告知被编辑个人并取得"单独同意"**——这不是内容标识，是肖像授权，做数字人主播项目绕不过去。
5. **[事实]** 《人工智能生成合成内容标识办法》已于 **2025-09-01 施行**，第四条对**视频**要求"起始画面和播放周边适当位置添加显著提示标识"，对**虚拟场景**要求"起始画面适当位置添加显著提示标识"；第五条要求在**文件元数据**中写入隐式标识（属性信息 + 服务提供者名称/编码 + 内容编号）。
6. **[事实]** 硅基智能的 HeyGem 仓库已迁移：**`GuijiAI/HeyGem.ai` 会 301 重定向到 `duixcom/Duix-Avatar`**（2026-09-29 经 GitHub API 实测），star 15,604，是本清单中 star 最高的国产口播方案。
7. **[推断]** 对"房产中介口播"这类**固定主播、固定场景、批量脚本**的场景，MuseTalk / LatentSync 路线（真人拍摄一段素材 + 后续只换音频）在成本、质量、合规三方面都优于单图生成路线；单图扩散路线（Hall/Sonic/EMO）的价值在于"没有真人可拍"或"需要大量非真人 IP 形象"时。
8. **[事实 + 缺口]** 本文件覆盖的 10 个开源方案 star 加总约 **8.4 万**（2026-09-29 实测求和，见 E-C-05）；但**行业规模数据本次未能核验到任何 IDC / 艾瑞 / 中国信通院的原始报告**（见 E-C-04 与文末「待核验清单」）。PPT 中不建议出现任何具体的市场规模亿元数字。

## 1. 开源口播数字人技术栈

### [E-A-01] MuseTalk（腾讯音乐娱乐 Lyra Lab）
- **事实**：音频驱动的实时唇形同步模型，在 `ft-mse-vae` 隐空间中做单步 inpainting，**官方明确声明不是扩散模型**；需输入**一段已有人脸视频/图像序列** + 音频，只改嘴部区域（人脸区域 256×256），不重绘全脸。
- **来源类型**：官方仓库 + 官方技术报告
- **证据等级**：A
- **来源**：
  - URL: https://github.com/TMElyralab/MuseTalk
  - 论文 URL: https://arxiv.org/abs/2410.10122
  - 发布日期: 2024-04-02（v1.0）；1.5 版 2025-03-28；训练代码开源 2025-04-05
  - 最后一次代码推送: **2025-09-26**（查询日 2026-09-29，⚠️ **可能过时**）
  - Star: **6,644**（查询日 2026-09-29，GitHub API 实测）
- **支撑细节**（README 原文要点）：
  - 速度：`supports real-time inference with 30fps+ on an NVIDIA Tesla V100`
  - 低配实测：`RTX 3050 Ti Laptop GPU with 4GB VRAM ... In fp16 mode, generating an 8-second video takes approximately 5 minutes`（约 37.5 秒生成 1 秒视频）
  - 训练显存（8×H20 实测）：stage1 batch32 ≈ 74GB/卡；stage2 batch2 ≈ 85GB/卡
  - 许可证（README Disclaimer/License 原文）：`The code of MuseTalk is released under the MIT License. There is no limitation for both academic and commercial usage.` / `The trained model are available for any purpose, even commercially.`
  - 官方自述局限：分辨率 256×256 未到理论上限；`Identity preservation: Some details of the original face are not well preserved, such as mustache, lip shape and color.`；`Jitter: There exists some jitter as the current pipeline adopts single-frame generation.`
- **我的推断**：**该仓库归属是"腾讯音乐娱乐（Lyra Lab）"，不是腾讯集团 CSIG/TEG**。PPT 中若写"腾讯出品"，需改为"腾讯音乐娱乐 Lyra Lab 团队"。**[推断] MuseTalk 是当前唯一同时满足"可商用许可 + 官方宣称实时 + 单卡可跑"的开源方案，是实习项目做实时交互数字人的首选底座**。
- **可用于 PPT**：✅（速度、显存、许可证、局限四条都可直接引用，务必带日期）

### [E-A-03] LatentSync（字节跳动）
- **事实**：端到端音频条件隐扩散唇形同步模型，**不使用任何中间运动表征**（无关键点、无 3D 参数），用 SyncNet 监督解决"视觉捷径学习"问题；开源了推理代码、训练代码、数据处理流水线和 checkpoint。
- **来源类型**：官方仓库 + 论文原文
- **证据等级**：A
- **来源**：
  - URL: https://github.com/bytedance/LatentSync
  - 论文 URL: https://arxiv.org/abs/2412.09262 （v1 2024-12-12，v2 2025-03-13）
  - Star: **6,102**（查询日 2026-09-29）
  - 许可证: **Apache-2.0**（GitHub API 实测）
  - 最后一次代码推送: **2025-06-20**（查询日 2026-09-29，⚠️ **可能过时**）
  - 版本: LatentSync 1.5 发布 2025-03-14；**LatentSync 1.6 发布 2025-06-11**（512×512 训练，缓解模糊）
- **支撑细节**（README 原文）：
  - 推理最低显存：`8 GB with LatentSync 1.5` / `18 GB with LatentSync 1.6`
  - 训练显存：stage1 23GB；stage2 30GB；**stage2_efficient 20GB（官方点名 "suitable for users with consumer-grade GPUs, such as the RTX 3090"）**；stage1_512 30GB；stage2_512 55GB
  - 发布的 SyncNet 在 VoxCeleb2 和 HDTF 上准确率 **94%**（README/论文：`increasing from 91% to 94% on the HDTF test set`）
  - 推理参数：`inference_steps` 20–50，`guidance_scale` 1.0–3.0
- **我的推断**：**[推断] LatentSync 是当前"画质 + 唇形准确度"平衡最好且许可证最干净（Apache-2.0）的开源方案，但实时性远不如 MuseTalk**（20–50 步扩散）。**[推断] 建议实习项目采用"MuseTalk 实时链路 + LatentSync 高质量离线链路"双通道。**
- **可用于 PPT**：✅（显存表可直接做 PPT 表格）

### [E-A-13] 监管口径：3D 数字人物被明确列为"深度合成技术"

- **可用于 PPT**：✅（合规页必引）

### [E-A-14] 技术路线差异：2D 照片级真人复刻
- **事实**：本节 E-A-01/03/09 三个方案（MuseTalk / LatentSync / Wav2Lip）均为 2D 路线，**共同前提是必须先有一段该真人的已拍摄视频**（MuseTalk README 的输入定义为 `video_path: Path to the input video, image file, or directory of images`；LatentSync 数据流水线为 `Affine transform the faces according to the landmarks detected by InsightFace`）；它们只替换口型区域，**保留原始视频的头部姿态、表情、服装、光照和背景**。
- **来源类型**：官方仓库（交叉验证三条）
- **证据等级**：A
- **来源**：
  - URL: https://github.com/TMElyralab/MuseTalk
  - URL: https://github.com/bytedance/LatentSync
  - URL: https://github.com/Rudrabha/Wav2Lip
- **我的推断**：**[推断] 2D 照片级路线的真实成本不在算法，在"素材"：每个主播需要一次合规的定向拍摄（正脸、光照均匀、25fps、无大幅遮挡），且此后所有内容的外观被这一次拍摄永久锁定。优点是身份一致性天然最高（像素级继承），几乎不会"变成另一个人"。**
- **可用于 PPT**：✅

### [E-A-15] 技术路线差异：单图扩散 / 端到端生成
- **事实**：Hallo / Sonic / FLOAT / EMO / OmniHuman-1 属于"单张参考图 → 整脸/全身动态"的生成路线。Hallo 论文声明 `Moving away from traditional paradigms that rely on parametric models for intermediate facial representations`；EMO 论文声明 `bypassing the need for intermediate 3D models or facial landmarks`；OmniHuman-1 摘要声明输入是 `a single human image and motion signals`。
- **来源类型**：论文原文
- **证据等级**：A
- **来源**：
  - URL: https://arxiv.org/abs/2406.08801 （Hallo）
  - URL: https://arxiv.org/abs/2402.17485 （EMO）
  - URL: https://arxiv.org/abs/2502.01061 （OmniHuman-1）
- **我的推断**：**[推断] 该路线的边际成本极低（一张照片即可出片，无需拍摄），但代价是：① 身份一致性由模型"想象"而非"继承"，长视频中易漂移；② 扩散/流匹配推理开销大，难实时；③ 幻觉出的面部细节（牙齿、眼镜反光）容易在观众侧产生" uncanny valley"观感。**
- **可用于 PPT**：✅

### [E-A-16] 3D 形象 + 动作库路线的可核验依据与其缺口
- **事实**：本次检索中，**唯一能直接核验的 3D 数字人官方材料是监管定义本身**（见 E-A-13 的"三维重建、数字仿真"条款）；GitHub 上未发现具有同等影响力（star ≥ 1k）的、口播用途的开源 3D 数字人动作库项目被本次检索覆盖。
- **证据等级**：B（缺口陈述，基于本次检索范围）
- **来源**：
  - URL: https://www.cac.gov.cn/2022-12/11/c_1672221949354811.htm
- **我的推断**：**[推断] 3D 路线在"口播"这个具体场景下的价值主要是风格化 IP（卡通/超写实虚拟主播）——因为真人复刻用 2D 照片级路线成本更低、效果更真；3D 的优势在多机位、互动场景（可实时驱动、可做游戏/展厅）、以及一次建模长期复用。本项目（AI 口播数字人）若目标是"像真人的房产中介口播"，2D 路线是更优解。**
- **可用于 PPT**：⚠️ 结论可用于 PPT，但需注明"3D 路线本轮未取得同等级开源证据"
